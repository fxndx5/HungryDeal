HungryDeal es una aplicacion web que resuelve un problema concreto del mercado del delivery en Espana: la opacidad de precios entre plataformas. Un mismo restaurante puede tener precios de producto, tarifa de envio y tarifa de servicio distintos en Uber Eats, Glovo y Just Eat. El usuario actualmente debe abrir tres aplicaciones distintas y comparar mentalmente el coste total. HungryDeal automatiza este proceso.

La arquitectura esta dividida en un backend REST con FastAPI (Python 3.11) desplegado en Render, y un frontend SPA con Next.js 14 desplegado en Netlify. La persistencia se gestiona con PostgreSQL alojado en Supabase. El sistema implementa el patron Adapter para abstraer cada plataforma, un sistema de cache Redis con TTL de 15 minutos, y autenticacion JWT.

Abstract: HungryDeal is a web application that compares in real time the total cost of ordering from the same restaurant across Spain's three main delivery platforms. It implements the Adapter design pattern, a Redis cache layer, JWT authentication, and comparison history tracking, deployed on Netlify and Render with a Supabase PostgreSQL database.

Capitulo 1

Introduccion y motivacion

1.1 Contexto

El mercado de delivery de comida en Espana mueve mas de 2.500 millones de euros anuales. Uber Eats, Glovo y Just Eat compiten por los mismos restaurantes y usuarios, pero con estructuras de precios diferentes y en muchos casos opacas. La tarifa de servicio varia entre el 5% y el 15% del valor del pedido y raramente aparece destacada en la interfaz hasta el momento de confirmar el pago.

Esta asimetria de informacion perjudica al consumidor: quien pide con frecuencia podria ahorrar entre 2 y 6 euros por pedido eligiendo la plataforma correcta.

1.2 Motivacion

El proyecto nace de la observacion directa de este problema. La solucion debe: (a) obtener precios reales de cada plataforma para un restaurante especifico, (b) calcular el coste total incluyendo todos los cargos, (c) presentar la comparacion de forma clara y accionable, y (d) recordar las comparaciones pasadas para mostrar tendencias al usuario.

1.3 Alcance

Plataformas cubiertas: Uber Eats (mock API), Glovo (mock API), Just Eat Espana (API interna real en api.just-eat.es). La integracion real de Uber Eats y Glovo requeriria acuerdos comerciales fuera del alcance academico de este TFG.
  • Busqueda de restaurantes por nombre o ciudad
  • Comparacion de precios con desglose por tarifa
  • Identificacion automatica de la plataforma mas barata
  • Historial de comparaciones por usuario autenticado
  • Mapa de restaurantes cercanos con filtros
  • Pagina de ofertas ordenada por maximo ahorro potencial
Capitulo 2

Objetivos

2.1 Objetivo principal

Desarrollar una aplicacion web funcional que compare el coste total de un pedido entre Uber Eats, Glovo y Just Eat para un restaurante dado, mostrando el desglose de cargos y la opcion mas economica.

2.2 Objetivos tecnicos

  • Implementar el patron de diseño Adapter para desacoplar la logica de negocio de cada plataforma
  • Disenar una API REST con FastAPI que respete los principios REST y OpenAPI
  • Persistir datos en PostgreSQL (Supabase) usando SQLAlchemy async con asyncpg
  • Implementar cache con Redis para reducir llamadas externas y mejorar latencia
  • Autenticacion segura con JWT (tokens con expiracion)
  • Despliegue en produccion con CI/CD automatico

Capitulo 4

Arquitectura del Sistema

El sistema sigue una arquitectura de tres capas con separacion clara entre presentacion, logica de negocio y persistencia. Los componentes se comunican exclusivamente mediante HTTP/JSON, permitiendo desplegar cada capa de forma independiente.

Figura 4.1. Arquitectura de tres capas del sistema HungryDeal

4.1 Comunicacion entre capas

El frontend se comunica exclusivamente con el backend a traves de llamadas HTTP al prefijo /api/v1/. El backend no expone directamente la base de datos; todo el acceso pasa por SQLAlchemy y los modelos ORM. La cache Redis actua como capa intermedia en el endpoint de comparacion, reduciendo la latencia de ~800 ms a ~15 ms para peticiones cacheadas.

Capitulo 5

Base de Datos en Supabase

Supabase es un Backend-as-a-Service basado en PostgreSQL que proporciona base de datos relacional gestionada, autenticacion integrada, API REST automatica y un dashboard web. HungryDeal utiliza exclusivamente la capa de base de datos de Supabase a traves de una conexion asyncpg directa con SQLAlchemy.

Capitulo 8

Patron de Diseño: Adapter

El patron Adapter es el nucleo arquitectonico del sistema. Define una interfaz abstracta DeliveryAdapter que todos los adaptadores de plataforma deben implementar. El PriceComparator trabaja exclusivamente contra esta interfaz, sin conocer los detalles de ninguna plataforma concreta.

Figura 8.1. Jerarquia del patron Adapter. JustEat usa API real
from abc import ABC, abstractmethod

class DeliveryAdapter(ABC):
    @abstractmethod
    async def get_prices(self, restaurant_id: str) -> dict: ...
Capitulo 9

Cache Redis

El sistema implementa cache Redis con degradacion elegante: si Redis no esta disponible al arrancar, la app continua funcionando sin cache, sin lanzar excepciones al cliente.

Figura 9.1. Flujo de cache Redis en el endpoint /compare
Degradacion elegante: Si Redis no responde al arrancar (timeout 2s), el atributo cache.available se establece a False. Todos los metodos get() y set() devuelven None silenciosamente. La app funciona con normalidad, simplemente sin cache.

10.2 Entornos: local (Docker) vs produccion (Supabase)

En local (Docker Compose): el backend arranca junto a un contenedor PostgreSQL y otro Redis. La DATABASE_URL apunta al contenedor db interno. Los datos son locales y efimeros (se pierden si se borra el volumen).

En produccion (Render + Supabase): el backend corre como servicio Docker en Render. La DATABASE_URL apunta al cluster PostgreSQL de Supabase, que persiste los datos en la nube y es accesible desde cualquier lugar. Redis corre como servicio adicional en el mismo docker-compose.prod.yml.

Flujo de registro: de la app a Supabase

Este carrusel muestra el flujo completo de registro de un nuevo usuario: desde el formulario en la aplicacion, hasta la aparicion del registro en la tabla users de Supabase, y la primera carga del perfil con estadisticas iniciales.

Que muestra este flujo: el usuario rellena el formulario de registro en la app → el frontend hace POST /api/v1/auth/register → el backend valida, hashea la contrasena con bcrypt y persiste en Supabase → se devuelve un JWT → el usuario queda autenticado y su perfil es visible en tiempo real.

Capitulo 14

Conclusiones

14.1 Objetivos alcanzados

  • Sistema full-stack completo con separacion clara de capas y principios SOLID.
  • El patron Adapter permite anadir nuevas plataformas sin modificar el nucleo del sistema.
  • La integracion real con la API interna de Just Eat Espana demuestra la viabilidad tecnica.
  • La cache Redis reduce la latencia de ~800 ms a ~15 ms para peticiones repetidas.
  • La aplicacion esta desplegada en produccion y es accesible publicamente.

14.2 Trabajo futuro

  • Integracion real con APIs de Uber Eats y Glovo mediante acuerdos de afiliacion.
  • Sistema de alertas: notificar cuando el precio de un restaurante favorito baja.
  • Aplicacion movil nativa con React Native reutilizando la misma API REST.
  • Analisis de tendencias de precios con historial temporal en una tabla price_history.
