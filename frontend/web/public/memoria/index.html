HungryDeal es una aplicación web que resuelve un problema concreto del mercado del delivery en España: la opacidad de precios entre plataformas. Un mismo restaurante puede tener precios de producto, tarifa de envio y tarifa de servicio distintos en Uber Eats, Glovo y Just Eat. El usuario actualmente debe abrir tres aplicaciones distintas y comparar mentalmente el coste total. HungryDeal automatiza este proceso.

La arquitectura esta dividida en un backend REST con FastAPI (Python 3.11) desplegado en Render, y un frontend SPA con Next.js 14 desplegado en Netlify. La persistencia se gestiona con PostgreSQL alojado en Supabase. El sistema implementa el patrón Adapter para abstraer cada plataforma, un sistema de cache Redis con TTL de 15 minutos, y autenticación JWT.

Abstract: HungryDeal is a web application that compares in real time the total cost of ordering from the same restaurant across Spain's three main delivery platforms. It implements the Adapter design pattern, a Redis cache layer, JWT authentication, and comparison history tracking, deployed on Netlify and Render with a Supabase PostgreSQL database.

Capítulo 1

Introducción y motivación

1.1 Contexto

El mercado de delivery de comida en España mueve más de 2.500 millones de euros anuales. Uber Eats, Glovo y Just Eat compiten por los mismos restaurantes y usuarios, pero con estructuras de precios diferentes y en muchos casos opacas. La tarifa de servicio varia entre el 5% y el 15% del valor del pedido y raramente aparece destacada en la interfaz hasta el momento de confirmar el pago.

Esta asimetria de información perjudica al consumidor: quien pide con frecuencia podria ahorrar entre 2 y 6 euros por pedido eligiendo la plataforma correcta.

1.2 Motivación

El proyecto nace de la observacion directa de este problema. La solución debe: (a) obtener precios reales de cada plataforma para un restaurante especifico, (b) calcular el coste total incluyendo todos los cargos, (c) presentar la comparación de forma clara y accionable, y (d) recordar las comparaciónes pasadas para mostrar tendencias al usuario.

1.3 Alcance

Plataformas cubiertas: Uber Eats (mock API), Glovo (mock API), Just Eat España (API interna real en api.just-eat.es). La integración real de Uber Eats y Glovo requeriria acuerdos comerciales fuera del alcance académico de este TFG.
  • Búsqueda de restaurantes por nombre o ciudad
  • Comparación de precios con desglose por tarifa
  • Identificacion automática de la plataforma más barata
  • Historial de comparaciónes por usuario autenticado
  • Mapa de restaurantes cercanos con filtros
  • Página de ofertas ordenada por máximo ahorro potencial
Capítulo 2

Objetivos

2.1 Objetivo principal

Desarrollar una aplicación web funciónal que compare el coste total de un pedido entre Uber Eats, Glovo y Just Eat para un restaurante dado, mostrando el desglose de cargos y la opción más económica.

2.2 Objetivos técnicos

  • Implementar el patrón de diseño Adapter para desacoplar la lógica de negocio de cada plataforma
  • Diseñar una API REST con FastAPI que respete los principios REST y OpenAPI
  • Persistir datos en PostgreSQL (Supabase) usando SQLAlchemy async con asyncpg
  • Implementar cache con Redis para reducir llamadas externas y mejorar latencia
  • Autenticación segura con JWT (tokens con expiracion)
  • Despliegue en producción con CI/CD automático
Capítulo 3

El mercado del delivery

3.1 Lo que existe hoy

En España no existe ninguna herramienta que compare el coste total de un pedido entre plataformas de delivery de forma automática y en tiempo real. El usuario que quiere saber si le sale más barato pedir en Uber Eats, Glovo o Just Eat tiene que abrir las tres aplicaciones por separado, calcular mentalmente la suma de precio del producto, tarifa de envío y tarifa de servicio, y comparar. HungryDeal elimina ese proceso.

El análisis anterior evidencia que la brecha que cubre HungryDeal no está siendo atendida por ningún competidor directo. La ventaja diferencial reside en tres aspectos técnicos concretos: acceso a la API interna no documentada de Just Eat España, normalización de precios entre plataformas con distintas estructuras de datos mediante el patrón Adapter, y una caché Redis con TTL de 15 minutos que hace el sistema sostenible sin sobrecargar las APIs de terceros.

Capítulo 4

Arquitectura del Sistema

El sistema sigue una arquitectura de tres capas con separación clara entre presentacion, lógica de negocio y persistencia. Los componentes se comunican exclusivamente mediante HTTP/JSON, permitiendo desplegar cada capa de forma independiente.

Figura 4.1. Arquitectura de tres capas del sistema HungryDeal

4.1 Comunicación entre capas

El frontend se comunica exclusivamente con el backend a traves de llamadas HTTP al prefijo /api/v1/. El backend no expone directamente la base de datos; todo el acceso pasa por SQLAlchemy y los modelos ORM. La cache Redis actua como capa intermedia en el endpoint de comparación, reduciendo la latencia de ~800 ms a ~15 ms para peticiones cacheadas.

Capítulo 5

Base de Datos en Supabase

Supabase es un Backend-as-a-Service basado en PostgreSQL que proporciona base de datos relacional gestionada, autenticación integrada, API REST automática y un dashboard web. HungryDeal utiliza exclusivamente la capa de base de datos de Supabase a traves de una conexión asyncpg directa con SQLAlchemy.

Patrón de Diseño: Adapter

El patrón Adapter es el núcleo arquitectonico del sistema. Define una interfaz abstracta DeliveryAdapter que todos los adaptadores de plataforma deben implementar. El PriceComparator trabaja exclusivamente contra esta interfaz, sin conocer los detalles de ninguna plataforma concreta.

Capítulo 9

Caché Redis

El sistema implementa cache Redis con degradacion elegante: si Redis no esta disponible al arrancar, la app continua funciónando sin cache, sin lanzar excepciones al cliente.

Figura 9.1. Flujo de cache Redis en el endpoint /compare
Degradacion elegante: Si Redis no responde al arrancar (timeout 2s), el atributo cache.available se establece a False. Todos los métodos get() y set() devuelven None silenciosamente. La app funcióna con normalidad, simplemente sin cache.

10.2 Entornos: local (Docker) vs producción (Supabase)

En local (Docker Compose): el backend arranca junto a un contenedor PostgreSQL y otro Redis. La DATABASE_URL apunta al contenedor db interno. Los datos son locales y efímeros (se pierden si se borra el volumen).

En producción (Render + Supabase): el backend corre como servicio Docker en Render. La DATABASE_URL apunta al cluster PostgreSQL de Supabase, que persiste los datos en la nube y es accesible desde cualquier lugar. Redis corre como servicio adicional en el mismo docker-compose.prod.yml.

Flujo de registro: de la app a Supabase

Este carrusel muestra el flujo completo de registro de un nuevo usuario: desde el formulario en la aplicación, hasta la aparicion del registro en la tabla users de Supabase, y la primera carga del perfil con estadísticas iniciales.

Que muestra este flujo: el usuario rellena el formulario de registro en la app → el frontend hace POST /api/v1/auth/register → el backend valida, hashea la contraseña con bcrypt y persiste en Supabase → se devuelve un JWT → el usuario queda autenticado y su perfil es visible en tiempo real.
Paso 1 de 4

Formulario de registro

El usuario introduce nombre, apellido, email y contraseña. El frontend valida el formato y muestra el estado "Creando cuenta..." mientras espera la respuesta del backend.

Paso 2 de 4

Registro en Supabase

La tabla users en Supabase muestra el nuevo registro con UUID generado, email, password_hash (bcrypt) y timestamps de creación. El registro test@test.com aparece resaltado en la ultima fila.

Paso 3 de 4

Perfil del usuario

Tras el registro, el usuario accede a su perfil. Las estadísticas parten en cero: 0 comparaciónes, 0,00 euros ahorrados, 0 restaurantes distintos.

Paso 4 de 4

Historial de comparaciónes

Cada vez que el usuario compara precios, el backend guarda la entrada en search_history. El tab Historial muestra las 10 comparaciónes realizadas, la plataforma ganadora y el ahorro conseguido en cada pedido.

Capítulo 14

Conclusiones

14.1 Objetivos alcanzados

HungryDeal demuestra que es técnicamente viable construir un comparador de precios de delivery que funciona con datos reales, sin depender de APIs públicas oficiales. Todos los objetivos planteados al inicio del proyecto han sido cubiertos:

  • Sistema full-stack completo con separación clara de capas y principios SOLID.
  • El patrón Adapter permite añadir nuevas plataformas sin modificar el núcleo del sistema: añadir el adapter de Just Eat no requirió tocar ni el comparador, ni los endpoints, ni el frontend.
  • La integración real con la API interna no documentada de Just Eat España demuestra la viabilidad técnica del enfoque.
  • La caché Redis reduce la latencia de respuesta de 1-2 segundos a menos de 50 ms en cache hit, haciendo el sistema usable en producción.
  • CI/CD automático mediante GitHub Actions garantiza que ningún cambio roto llega a producción.
  • La aplicación está desplegada y es accesible públicamente en hungrydeal.netlify.app.

Desde el punto de vista académico, este proyecto ha permitido aplicar en un contexto real los conceptos de diseño de software estudiados durante el ciclo: patrones de diseño GoF, principios SOLID, arquitectura en capas y separación de responsabilidades. La diferencia respecto a un ejercicio de clase es que cada decisión tiene consecuencias reales: un bug en el adapter corta el servicio en producción; un test que no cubre un caso deja pasar un error al pipeline.

14.2 Dificultades encontradas

  • Reverse engineering de la API de Just Eat: la API no está documentada y los headers necesarios se identificaron analizando el tráfico de red de la app móvil oficial.
  • Compatibilidad de z-index con Leaflet: los componentes del mapa usan z-index de hasta 1000. Se resolvió con isolation: isolate en el contenedor del mapa.
  • Rutas @shared en Netlify: el monorepo con frontend/shared fuera del directorio de Next.js causaba errores de build. Se resolvió moviendo los archivos a frontend/web/lib/.

14.3 Trabajo futuro

La arquitectura basada en el patrón Adapter hace que añadir nuevas plataformas sea una tarea de implementación localizada, sin impacto sobre el resto del sistema. Las siguientes mejoras están priorizadas por impacto en el usuario:

  • Adapter para Glovo y Uber Eats, completando la comparación entre las tres plataformas principales.
  • Sistema de alertas: notificación push cuando el precio de un restaurante favorito baja en alguna plataforma.
  • Aplicación móvil nativa con React Native reutilizando la misma API REST.
  • Análisis de tendencias de precios con historial temporal persistido en price_history.
  • Programa de afiliación: comisión por cada redirect que termina en pedido real.
